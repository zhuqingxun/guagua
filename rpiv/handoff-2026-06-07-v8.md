**复核方式**：删除现有配对 → 手柄进入 Share+PS 快闪配对模式 → 用交互式 `bluetoothctl`（管道 stdin 模拟手动逐行输入，非一次性 CLI 子命令）走卖家文档标准四步 `scan on → pair → trust → connect`，全程 btmon + bluetoothd journal 抓包对照。

**回答两个存疑点**：
- **(a) 交互式默认 agent 够不够？够。** 不需要显式 `bt-agent -c NoInputNoOutput` 也能 `Connected: yes`。
- **(b) `scan on` 能否扫到这台手柄？扫不到，确认。** `pair` 一开始报 `not available`；设备是在配对模式下自己主动发起连接，被 BlueZ 动态记录为 `[NEW]`，不是靠 host inquiry 发现的。

**新发现的真正根因（超出原两个假设，是本次复核最大收获）**：卖家标准四步协商出的是 `Paired: yes / Bonded: no`（host 请求 "No Bonding"）。`bluetoothd` 日志实锤：`profiles/input/device.c:hidp_add_connection() Rejected connection from !bonded device`——**HID input profile 明确拒绝为非 bonded 设备建立连接**，这才是"看起来连上了但 js0 死活不出现"的真正机制。必须用 `bt-agent -c NoInputNoOutput` 协商出 `General Bonding` 才能同时满足"连接成功"+"HIDP 愿意建立"两个条件。

**结论**：我们此前(6/7)用 NoInputNoOutput 的方案是必需的，不是绕远路；卖家文档对这台副厂手柄不完整（能连但不能用）。完整结论+可复用命令已写入 [docs/duck-ps4-ds4drv-recovery.md](../docs/duck-ps4-ds4drv-recovery.md)。

**额外验证**：复核后顺手重新配对(NoInputNoOutput → Bonded: yes → js0 出现)，并手动启动了 RL 走路控制进程（系统重置后 customizations 未部署，无自启服务），端到端验证 right_knee(ID13) 舵机寄修更换后走路正常，用户确认"一切正常"。详见 [docs/duck-workspace-state.md](../docs/duck-workspace-state.md) §7。
